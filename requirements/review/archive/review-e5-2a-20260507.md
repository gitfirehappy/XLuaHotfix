## Findings

### 1. High: `TaskBuildBundles` drops scene bundle outputs and records incorrect metadata

> **Status**: ✅ RESOLVED (2026-05-07) — scene output index + `PayloadKind.Scene` per-output tracking implemented

- File: `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskBuildBundles.cs:65-107,136-170`

Scene assets are split into separate Unity bundle build entries:

```csharp
assetBundleName = bundleName + "_scene_" + s
```

But result collection later iterates only `groups.Keys` and keeps a single first prefix match per logical bundle:

```csharp
foreach (var logicalName in groups.Keys)
{
    if (allBundles[i].StartsWith(logicalName, ...))
    {
        matchedFile = allBundles[i];
        break;
    }
}
```

That produces two correctness problems:

1. multiple scene outputs under the same logical group are collapsed into one `BundleBuildInfo`
2. the recorded `PayloadKind` is always `Serialized`, even when the matched output is a scene bundle

This is not just reporting drift. `BundleBuildInfo` is the handoff contract into E6, so missing or misclassified scene outputs will propagate into manifest generation.

**Recommendation**: collect results from the actual `AssetBundleBuild` entries or from `unityManifest.GetAllAssetBundles()` one-by-one, keeping scene outputs as distinct `BundleBuildInfo` records with the correct `PayloadKind`.

### 2. Medium: `TaskCollectBuiltins` can add folder entries from `Assets/Resources`

> **Status**: ✅ RESOLVED (2026-05-07) — `IsValidFolder` guard added

- File: `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskCollectBuiltins.cs:23-25,63-100`

For the Resources category, the task uses:

```csharp
AssetDatabase.FindAssets("", new[] { "Assets/Resources" })
```

and then directly appends every returned GUID to `CollectedAssets` without guarding against folders:

- no `AssetDatabase.IsValidFolder(path)` check
- no `DefaultAsset` exclusion

If the search returns folder GUIDs under `Assets/Resources`, the task will inject directory entries as `Serialized` assets into the build graph. Unlike `CollectionScanner`, this path does not go through rule-based filtering first.

**Recommendation**: explicitly skip folders and other non-buildable assets before creating `CollectedAssetInfo`.

### 3. Medium: multi-file `RawFile` bundles are effectively reduced to a single copied file

> **Status**: ✅ RESOLVED (2026-05-07) — fail-fast enforcement: `RAWFILE_MULTI_ASSET` error on multi-file raw bundles

- File: `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskBuildBundles.cs:176-205`

`rawFileEntries` stores one `(bundleName, assetPath)` tuple per raw asset, but copy/output handling is keyed only by `bundleName`:

```csharp
if (processedNames.Contains(bundleName))
    continue;
```

After the first raw file for a given bundle name is copied, every additional raw file in that same bundle is skipped. This only works if the pipeline guarantees "one raw file per bundle". I did not find that guarantee enforced here.

If pack rules ever group multiple raw files into the same bundle name, E5-2a will silently produce incomplete output.

**Recommendation**: either enforce the single-raw-file invariant explicitly and fail fast, or implement a bundling/copy layout that supports multiple raw-file assets per bundle.
