## Findings

### 1. High: `TaskGenerateManifest` 声明读取 `BuildVersion`，实际却绕过 BuildContext 改读 `VersionDataBase.asset`

> **Status**: 🔷 DEFERRED — 纳入 version 统一管理优化草案，后续收束为精确计划

- File: `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskGenerateManifest.cs:27-30,168-172,197-204`

E6 计划把 `BuildVersion` 放在 `ReadKeys` 中，说明 manifest 版本应该来自管线输入。但当前实现只是：

```csharp
string buildVersion = ctx.Require<string>(BuildContextKeys.BuildVersion);
```

随后完全不使用这个值，而是：

```csharp
PackageVersion = ResolveVersion()
```

`ResolveVersion()` 又直接回到 `Assets/Build/VersionDataBase.asset` 读取 `CurrentVersion`。

这会带来两个问题：

1. `TaskPrepareContext` 写入的版本上下文不再是单一事实源，CLI / 调度输入与最终 manifest 版本可能不一致。
2. 调度器的 `ReadKeys` 契约变成“声明读取但并未真正消费”，后续看 DAG 配置的人会被误导。

这不是单纯的实现偏差，而是会直接影响运行时热更版本判断的数据正确性。

**Recommendation**: 要么真正从 `BuildVersion` 解析 `VersionNumber`，要么把版本来源明确前移成单独 Task 并写入强类型 key；不要在 `TaskGenerateManifest` 内部重新读 SO。

### 2. High: CRC32 文件缺失时被静默写成 `0`，E6 没有把完整性缺口当作错误

> **Status**: ✅ RESOLVED (2026-05-07) — 文件缺失时返回 `Fail("BUNDLE_FILE_NOT_FOUND")`，不再静默写 0

- File: `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskGenerateManifest.cs:41-49`

当前逻辑是：

```csharp
if (File.Exists(filePath))
    crc = CRC32Helper.Compute(filePath);
```

如果文件不存在，`crc` 保持默认值 `0`，然后这个 bundle 仍然会进入 `ManifestBundleEntry`：

```csharp
FileCRC = crc
```

这会把“构建产物缺失”降级成一个看起来合法的 manifest 条目，而不是中止构建。E6 计划里的 invariant 是“FileCRC 从实际文件计算”，但现在变成了“算得到就算，算不到就写 0”。

考虑到 E5-2a 当前已经存在 scene 输出折叠问题，这里进一步静默吞掉缺失文件，会把错误带到 runtime 才暴露。

**Recommendation**: 对每个 `BundleBuildInfo` 强制校验目标文件存在；缺失时直接 `Fail("BUNDLE_FILE_NOT_FOUND", ...)`，不要写 `0` CRC 继续。

### 3. Medium: `ManifestBundleEntry.Tags` 的运行语义和 E6 写入语义互相冲突

> **Status**: ✅ RESOLVED (2026-05-07) — 清除 Labels→Tags 自动聚合，更新 `ManifestBundleEntry.Tags` 注释，Tags 保留为纯下载策略标签

- Files:
  - `Assets/FYAsset/Scripts/Runtime/Models/ManifestBundleEntry.cs:46-50`
  - `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskGenerateManifest.cs:149-164`

`ManifestBundleEntry` 现在的注释明确写的是：

- `Tags` 是“Bundle 级下载策略标签”
- “不是 Asset Labels 的聚合”

但 `TaskGenerateManifest` 实际做的是：

```csharp
// Bundle 内资产 Labels 去重并集
tagSet.Add(labels[l]);
bundleEntries[bi].Tags = new List<string>(tagSet);
```

也就是说，落地代码内部已经出现了明确的语义对撞：

1. runtime model 说 `Tags` 不是 Asset Labels 聚合
2. build task 却正是在做 Asset Labels 聚合

这会直接影响后续 E5-2b / 增量下载 / runtime 侧对 `Tags` 的理解。现在不是“将来再定义”，而是已经写入了一套相反的数据。

**Recommendation**: 二选一并尽快统一：

- 如果 `Tags` 就是 asset labels union，那么更新 `ManifestBundleEntry` 注释和相关计划说明。
- 如果 `Tags` 是下载策略标签，那么 E6 现在不应从 asset labels 自动聚合它。

### 4. Medium: E6 缺少针对 `TaskGenerateManifest` 的自动化验证，现有 round-trip 只覆盖序列化字段

> **Status**: ⚠️ RECOMMENDATION — 测试覆盖暂未实施

- Evidence:
  - 当前未发现针对 `TaskGenerateManifest` / `CRC32Helper` 的独立自动化测试。
  - `ABManifestRoundTripTest` 是编辑器菜单驱动的 round-trip 验证，不会自动校验 E6 的映射逻辑、版本来源、CRC 缺失路径、依赖索引解析或 Tag 语义。

E6 真正的风险不在“string 字段能否序列化”，而在“构建期如何装配出正确 manifest”。这部分现在基本没有回归保护。

**Recommendation**: 至少补 4 类 editor tests：

- `BuildVersion` / `VersionDataBase` 冲突时的版本来源校验
- bundle 文件缺失时应失败
- `DependBundleIndices` 解析正确
- `Tags` / `BundleType` 生成规则
