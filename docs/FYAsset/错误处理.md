# 错误处理

> **关联代码** | [RuntimeMessage](../../Assets/FYAsset/Scripts/Shared/Runtime/RuntimeMessage.cs) · [BuildMessage](../../Assets/FYAsset/Scripts/Shared/Build/Editor/Common/BuildMessage.cs) · [HotfixFatalException](../../Assets/FYAsset/Scripts/Shared/Hotfix/HotfixFatalException.cs)

构建诊断与运行时诊断分别使用 BuildMessage、RuntimeMessage，不共用基类。两者以 Severity、Code、Message 表达信息；构建诊断另有 Source，运行时冲突可以携带 Candidates。

## 返回形式

| 边界 | 调用方处理 |
|---|---|
| Collector/依赖分析 | 检查消息集合与 HasErrors，不把存在 Warning 等同于构建可成功 |
| BuildTaskResult | Success 和 IsFatal 分开；非 Fatal 失败可继续后续 Task，但总结果仍失败 |
| BuildResult/BuildBackendResult | 汇总任务和后端失败，报告写入失败不能覆盖原始构建结果 |
| tuple 加载 | 检查 `(asset, error)`，不要将其他 API 的契约照搬过来 |
| AssetHandle<T> | 检查 IsValid/Error，显式管理 Retain/Release |
| HotfixStepResult | 检查 Success；default 为失败且 Error 可为空 |
| HotfixFlowBase | 致命失败通过 HotfixFatalException 传播；警告、错误和完成事件是另一路通知 |

现有具体 Backend 并非所有公开方法都捕获所有异常。没有现存 IPackageBackend 或 AddressablesBackend 抽象可以提供统一“不抛异常”承诺。I/O、Unity 调用及订阅者回调仍可能抛出。

## 诊断不是验证器

工厂方法统一构造消息，但通用 Error/Warning 仍接受任意 code/message；这不保证 Code 来自常量或描述准确。Severity 表示调用方的分类，不证明其他资产或后续动作一定正确。

RuntimeMessage 的 Serializable 标记不能证明 Unity 会序列化其 readonly 字段，也不能证明跨域传递或 Inspector 展示能力。此类保证需要独立的使用实现与验证。

## 资源与文件失败

HandleRegistry 在 EntryId 最后一个活动 slot 释放时调用后端回调；不要用直接 Unload 绕过仍活跃的 Handle。释放回调失败时也不能仅凭 Generation 机制认定资源全部释放。

FileHelper 的读取和原子写可能抛 I/O 异常；TryDelete/TryDeleteDirectory 将通常的删除失败转换为 false 和日志。单文件原子替换不提供多文件提交原子性。临时文件可能在进程中断后残留。

交付/发布的补偿也是文件操作，可能再次失败。日志应区分原始失败和补偿失败，不把“已尝试回滚”写成“必然恢复成功”。错误码的完整清单以源码为准，避免在文档复制一份易过时的常量表。
