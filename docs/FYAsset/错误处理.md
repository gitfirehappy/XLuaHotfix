# 错误处理

> **关联代码** | [RuntimeMessage](../../Assets/FYAsset/Scripts/Shared/Runtime/RuntimeMessage.cs) · [BuildMessage / BuildErrorCodes](../../Assets/FYAsset/Scripts/Shared/Build/Editor/Common/BuildMessage.cs) · [BuildPipelineException](../../Assets/FYAsset/Scripts/Shared/Build/Pipeline/Editor/BuildPipelineException.cs) · [HotfixFatalException](../../Assets/FYAsset/Scripts/Shared/Hotfix/HotfixFatalException.cs) · [HotfixStepResult](../../Assets/FYAsset/Scripts/Shared/Hotfix/HotfixStepResult.cs)

构建诊断与运行时诊断分别使用 `BuildMessage`、`RuntimeMessage`，不共用基类。两者都以 Severity、Code、Message 表达信息；构建诊断另有 Source，运行时消息可承载具体对象（EntryId / 文件名 / 路径）。

---

## 返回形式

| 边界 | 调用方处理 |
|---|---|
| Collector / 依赖分析 | 检查消息集合与是否存在 Error；有 Warning 不等于构建可成功 |
| `BuildTaskResult` | `Success` 与失败码分开；**Runner 对任何失败都停止后续 Task**（`IsFatal` 目前只作为结果字段，不改变调度），剩余 Task 标 `Skipped` |
| `BuildRunResult` | 汇总成功状态、参与/完成/跳过数量、逐个 Task 结果与交付 token |
| `BuildPipelineException` | Composer 组装失败或运行环境初始化失败；**一律致命**，不存在“跳过非法条目继续构建”的降级路径 |
| `BuildResult` | 汇总后端失败与 `CompleteBuildSummary`；报告写入失败不能覆盖原始构建结果 |
| `AssetHandle<T>` / `SceneHandle` | 检查 `IsValid` / `Error`，显式管理 Retain/Release |
| `HotfixStepResult` | 检查 `Success`；default 为失败且 Error 可为空 |
| `HotfixFlowBase` | 致命失败通过 `HotfixFatalException` 传播；`OnWarning` / `OnError` / `OnClientUpdateRequired` / `OnFinished` 是另一路通知 |
| `PushReceipt` | 检查 `Success` 与 `FailureReason` / `DegradedToFullUpload` |

现有具体 Backend 并非所有公开方法都捕获所有异常；没有现存的统一“不抛异常”抽象。I/O、Unity 调用及订阅者回调仍可能抛出。

## 构建错误码

`BuildErrorCodes`（`Shared/Build/Editor/Common/BuildMessage.cs`）按用途分组：

| 分组 | 码 |
|---|---|
| 配置校验 | `SETTING_NULL`、`NO_GROUPS`、`EMPTY_GROUP_NAME`、`DUPLICATE_GROUP_NAME`（Warning）、`INVALID_ASSET_OVERRIDE_GUID`、`BLANK_CONFIG_ENTRY`、`EMPTY_COLLECT_PATH`、`PATH_NOT_FOUND`、`SAME_PATH_CONFLICT`、`INVALID_BUNDLE_NAME_SEGMENT`、`INVALID_BUNDLE_ENTRY_ASSET`、`INVALID_LABEL`、`EMPTY_COLLECTOR`、`DUPLICATE_GUID` |
| 采集与依赖 | `COLLECT_ASSETS_FAILED`、`NO_COLLECTED_ASSETS`、`DEPENDENCY_ANALYSIS_FAILED`、`SHAREPOLICY_CONFLICT`、`SHAREPOLICY_SIZE_UNKNOWN`、`CYCLE_DEPENDENCY`、`CYCLE_COUNT`、`CYCLE_TRUNCATED` |
| 内容构建 | `RAWFILE_PAYLOAD_CONFLICT`、`MIXED_PAYLOAD_BUNDLE`、`MIXED_PRIMARY_TYPE_BUNDLE`、`RAWFILE_MULTI_ASSET`、`RAWFILE_COPY_FAILED`、`BUNDLE_FILE_NOT_FOUND`、`BUNDLE_NOT_FOUND_BUILD`、`DUPLICATE_BUNDLE_NAME` |
| Manifest | `MANIFEST_INIT_FAILED`、`MANIFEST_DEPENDENCY_CONFLICT`、`DUPLICATE_MANIFEST_MEMBERSHIP`、`MANIFEST_MEMBERSHIP_MISSING`、`MANIFEST_PAYLOAD_MISMATCH` |
| 管线装配（Composer） | `NO_PIPELINE_TASKS`、`CORE_TASK_SLOT_MISSING`、`CORE_TASK_SLOT_EMPTY`、`CORE_TASK_SLOT_DUPLICATE`、`CUSTOM_TASK_SLOT_UNKNOWN`、`CUSTOM_TASK_NAME_EMPTY`、`CUSTOM_TASK_NAME_DUPLICATE`、`CUSTOM_TASK_NAME_CONFLICTS_CORE`、`TASK_NOT_FOUND`、`TASK_RESOLUTION_FAILED` |
| 执行（Runner） | `NULL_RESULT`（Task 返回 null）、`TASK_EXECUTION_ERROR`（Task 抛异常）、`BUILD_FAILED`（环境初始化 / attempt 提升失败）、`INVALID_PLATFORM`、`INVALID_BACKEND`、`LUA_INDEX_INVALID`、`MISSING_BACKBONE_TASK` |
| 校验 | `VERIFICATION_FAILED` |

`BuildVerificationIssueCodes` 是**校验项**代码，不等同于 Task 失败码：`FILE_EXISTENCE`、`FILE_INTEGRITY`、`HASH_RE_VERIFY`、`CRC_VERIFY`、`SIZE_VERIFY`、`SIZE_ANOMALY`、`ORPHAN_CHECK`、`COUNT_CROSS_CHECK`、`ADDRESS_UNIQUENESS`、`PUBLIC_BOUNDARY`、`ASSET_CONTENT_MEMBERSHIP`、`CONTENT_TYPE_CHECK`、`DEPENDENCY_INDICES`、`FILE_SET_MATCH`。

### Composer / Runner 的错误语义

| 阶段 | 错误码 | 触发条件 |
|---|---|---|
| Composer | `CORE_TASK_SLOT_*` | 主干槽位名为空、重复，或槽位没有主干 Task 实例 |
| Composer | `NO_PIPELINE_TASKS` | 主干定义为空，或 Runner 收到的 Task 列表为空 |
| Composer | `CUSTOM_TASK_SLOT_UNKNOWN` | 自定义 Task 未声明 Slot，或 Slot 不是合法槽位 |
| Composer | `CUSTOM_TASK_NAME_*` | TaskName 为空、重复，或与主干同名 |
| Composer | `TASK_NOT_FOUND` / `TASK_RESOLUTION_FAILED` | 自定义 TaskName 无实现 / 有实现但构造失败 |
| Runner | `TASK_EXECUTION_ERROR` | Task 抛异常，或运行环境 `PrepareContext` 抛出非管线异常 |
| Runner | `NULL_RESULT` | Task 返回 null |
| Runner | `BUILD_FAILED` | `BeginAttempt` 失败，或 `TryPromote` 提升失败（正式输出保持原状） |

`BuildPipelineException` 携带 `Code`，`Message` 直接面向使用者说明哪一条输入不合法（构造时拼成 `[CODE] message`）；调用方（AA/AB 后端与编辑器面板）按约定显示为红色文本。

## 运行时错误码

`RuntimeErrorCodes`：

| 码 | 含义 |
|---|---|
| `NOT_FOUND` | 未找到匹配查询条件的条目 |
| `LOAD_FAILED` | Resolve 成功但底层加载失败 |
| `BUNDLE_NOT_FOUND` | Bundle 文件在当前激活包根下不存在 |
| `BUNDLE_LOAD_FAILED` | `AssetBundle.LoadFromFile` 返回 null |
| `DEPENDENCY_FAILED` | 依赖 Bundle 加载失败（级联） |
| `ASSET_EXTRACTION_FAILED` | 从 Bundle 提取 Asset 失败 |
| `INVALID_PAYLOAD_KIND` | 请求的加载 API 与 `AssetContentType` 不匹配 |
| `UNSUPPORTED_OPERATION` | 当前后端或平台不支持该操作 |
| `DUPLICATE_ADDRESS` | 公共 Address 在同一包内重复（大小写不敏感） |
| `ACTIVE_HANDLES_REMAIN` | 关闭或切换资源管理器时仍有活跃 Handle |
| `SCENE_LOAD_FAILED` | Scene 加载、校验或卸载失败 |
| `INVALID_ARG` | 参数无效 |

三个结构化阻断点值得单独说明：

1. **`DUPLICATE_ADDRESS`**：`ABAssetIndex` 构建时发现公共 Address 重复 → `BuildError` 非 null、`IsValid` 为 false，**清空全部查询索引**；`ABPackageManager.InitializeFromManifest` 据此拒绝初始化。构建期同一条件由 `ADDRESS_UNIQUENESS` 校验先行阻断。
2. **`ACTIVE_HANDLES_REMAIN`**：`ABPackageManager.Shutdown()` 与热更 Apply 门禁都会返回该错误，并携带 Asset/Scene 计数。此时**不做任何释放**，由业务先释放 Handle。
3. **`SCENE_LOAD_FAILED`**：场景加载或卸载失败时返回；`SceneHandle.UnloadAsync` 会把 Warning 记日志、Error 记错误日志并返回 false。

## 热更失败传播

- 致命失败通过 `HotfixFatalException` 抛出并终止启动；`HotfixStepResult.Fail(RuntimeMessage)` 承载可继续处理的失败。
- 需 Warning 的情形：远端不可用、退化到内置完整包、本地指针不可信、远端拒绝前向切换、Apply 门禁拒绝、旧包清理失败。
- `OnClientUpdateRequired((ClientVersion, RemoteVersion, TargetPackageName))` 只在远端 Major 更高时触发。
- 启动阶段的 `RunAsync` 把未预期异常统一转换为致命错误；运行中 `Check/Prepare/Apply` 返回结果而不是抛异常。
- 目标包准备失败时删除目标目录；激活或初始化失败时不写本地 `PackageIndex`，并尝试恢复此前完整包，恢复失败返回阻断错误。删除与补偿本身也可能失败。

## 发布退化原因

`PublishPlan.DegradeReason` 非空即表示本次退化为**完整上传**（`IsFullUpload`）。代码中会产生退化的具体原因：

| 原因类别 | 示例说明 |
|---|---|
| 服务器 PackageIndex 不可用 | 文件不存在、反序列化为空、缺少 `LatestVersion` 对象、读取异常 |
| 索引未指向可用包 | `LatestPackage` 为空，或包名不是合法目录名 |
| 服务器包目录不存在 | `{packagesRoot}/{LatestPackage}` 缺失 |
| 服务器 Manifest 损坏或缺失 | `IPackageManifestReader.TryReadContentDigests` 返回 false |
| 服务器包缺少清单文件或不可读 | `RequiredPackageFileNames` 中的文件摘要不可用 |
| 服务器包内容与其 Manifest 不一致 | 存在清单未声明的文件，或文件与清单摘要不一致 |

退化只影响“上传多少”，不影响正确性：发布仍然先在隔离目录组装并校验，再就位、最后写 `PackageIndex`。发布缓存与服务器事实不一致时只输出提示，不改写 `DegradeReason`。

## 诊断不是验证器

工厂方法统一构造消息，但通用 `Error` / `Warning` 仍接受任意 code/message；这不保证 Code 来自常量或描述准确。Severity 表示调用方的分类，不证明其他资产或后续动作一定正确。

`RuntimeMessage` 的 `[Serializable]` 标记不能证明 Unity 会序列化其 readonly 字段，也不能证明跨域传递或 Inspector 展示能力；此类保证需要独立的使用实现与验证。

---

## 资源与文件失败

`HandleRegistry` 在 EntryId 最后一个活动 token 释放时调用后端回调；不要用直接 Unload 绕过仍活跃的 Handle。释放回调失败时也不能仅凭 Generation 机制认定资源全部释放。

`FileHelper` 的读取和原子写可能抛 I/O 异常；`TryDelete` / `TryDeleteDirectory` 把通常的删除失败转换为 false 和日志。单文件原子替换不提供多文件提交原子性；临时文件可能在进程中断后残留。

交付与发布的补偿同样是文件操作，可能再次失败。日志区分原始失败和补偿失败，不把“已尝试回滚”写成“必然恢复成功”。错误码的完整清单以源码为准，避免在文档复制一份易过时的常量表。
