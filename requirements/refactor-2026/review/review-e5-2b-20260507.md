## Findings

### 1. High: `TaskVerifyBuildResult` 和 `TaskOrganizeOutput` 只按 `*.bundle` 处理文件，和当前 E5-2a/E6 产物模型不兼容

> **状态**: ✅ 已解决 (2026-05-07) — `TaskVerifyBuildResult` 改为以 `Manifest.BundleEntries` 为来源逐项校验，`TaskOrganizeOutput` 改为以 `Manifest.BundleEntries` 为来源逐项拷贝

- Files:
  - `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskVerifyBuildResult.cs:35-38,117-137`
  - `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskOrganizeOutput.cs:37-48`

当前实现把临时输出目录中的待验证/待拷贝文件限定为：

```csharp
Directory.GetFiles(tempDir, "*.bundle")
```

但 E5-2a / E6 的当前数据契约并不是“所有输出都一定以 `.bundle` 结尾”：

- `TaskBuildBundles` 的 `BundleBuildInfo.OutputFileName` 被直接写入 manifest
- RawFile 路径仍然可能使用逻辑 bundle 名而不是显式 `.bundle`
- Scene 输出名和 serialized 输出名已经是构建产物真实文件名，而不是固定靠扩展名筛选

结果就是：

1. `TaskVerifyBuildResult` 的 orphan/count 校验只统计 `.bundle` 文件，非 `.bundle` 产物会被直接漏掉
2. `TaskOrganizeOutput` 也只拷贝 `.bundle` 文件，manifest 中存在但扩展名不同的产物不会进入最终输出目录

这不是边角问题，而是 E5-2b 对“什么算构建产物”的判断和前序任务的实际契约不一致。

**Recommendation**: 不要靠 `*.bundle` 扫目录；以 `BundleBuildResults` / `ABManifest.BundleEntries` 为来源逐项验证和逐项拷贝，文件系统枚举只用于补充 orphan 检查。

### 2. High: `TaskVerifyBuildResult` 的 “FILE_INTEGRITY” 并未实现计划中的 “Unity header 可读”

> **状态**: ✅ 已解决 (2026-05-07) — UnityFS header magic 校验已实现

- File: `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskVerifyBuildResult.cs:67-79`

计划里定义的第 2 项检查是：

- 文件大小 > 0
- Unity header 可读

当前实现只做了这一半：

```csharp
if (fileInfo.Length == 0)
```

没有任何 header / 可加载性验证。也就是说，损坏但非空的 bundle 会通过这一项，直到后续 runtime 或 Unity 加载阶段才暴露。

这会让 `TaskVerifyBuildResult` 的名字和实际保障能力不匹配。

**Recommendation**: 如果要保留 “FILE_INTEGRITY” 这个检查名，就补真正的 header / bundle 可读性校验；否则应把计划和代码都降级成“non-empty file check”。

### 3. Medium: `TaskOrganizeOutput` 没有把计划要求的关键摘要字段真正写入 `build_summary.txt`

> **状态**: ✅ 已解决 (2026-05-07) — `TargetPlatform` 与 `BackendMode` 已添加到 `ReadKeys` 并写入 summary

- File: `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskOrganizeOutput.cs:56-87`

计划要求摘要至少包含：

- 版本号
- 时间戳
- 平台
- 后端模式
- bundle 数量 / 总大小 / 资产数量
- warning / error 摘要

当前实现只写了：

- `BuildVersion`
- `manifest.BuildTimestamp`
- bundle 数
- 总大小
- asset 数
- copied file 数
- verification 摘要

缺失了两个关键上下文字段：

1. `TargetPlatform`
2. `BackendMode`

这会让最终输出目录里的摘要文件失去最重要的构建可追溯信息之一，尤其是这个项目同时维护 Legacy / ABManifest 两套链路。

**Recommendation**: `TaskOrganizeOutput.ReadKeys` 增加 `TargetPlatform` 与 `BackendMode`，并将其写入 summary。

### 4. Medium: `BuildVerificationResult` 引入了 LINQ-only 统计属性，但该结构会被构建管线热路径消费

> **状态**: ✅ 已解决 (2026-05-07) — `ErrorCount` / `WarningCount` 改为构造时直接写入字段，不再使用 LINQ

- File: `Assets/FYAsset/Scripts/Build/Pipeline/Editor/BuildVerificationResult.cs:1-14`

`ErrorCount` / `WarningCount` 目前是：

```csharp
Issues.Count(i => i.Level == IssueLevel.Error)
Issues.Count(i => i.Level == IssueLevel.Warning)
```

这会在每次访问时重新遍历，并依赖 LINQ。对 editor-only 工具这不是 correctness bug，但和本代码库在 pipeline/runtime 里反复强调的 “避免不必要 LINQ / 明确数据结构” 风格不一致。

这里更实际的问题是：`TaskVerifyBuildResult` 和 `TaskOrganizeOutput` 都会重复读取这两个属性，问题数量一多时会反复扫描列表。

**Recommendation**: 在构建 `BuildVerificationResult` 时直接写入 `ErrorCount` / `WarningCount` 字段，或者提供一次性统计方法。

### 5. Medium: E5-2b 缺少针对验证与输出组织逻辑的自动化测试

> **状态**: ⚠️ 建议 — 测试覆盖暂未实施

- Evidence:
  - 当前未发现针对 `TaskVerifyBuildResult` / `TaskOrganizeOutput` / `BuildVerificationResult` / `HashGenerator` 新增调用面的专门测试。
  - 本地确认的验证仍然主要是 `dotnet build` 成功。

E5-2b 的风险不是“能不能编译”，而是“产物缺失、Hash 错误、错误文件、临时目录清理、最终输出目录布局”这些流程行为是否真的闭合。现在这部分没有回归保护。

**Recommendation**: 至少补以下 editor tests：

- 非 `.bundle` 输出文件仍能被 verify / organize 正确处理
- hash mismatch 会 fatal
- orphan file 会 warning
- summary 包含平台 / backend / verification 统计
- `_temp` 清理失败时不会导致误报成功
