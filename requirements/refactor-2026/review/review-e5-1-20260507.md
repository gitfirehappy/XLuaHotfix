## Findings

### 1. High: `Read-before-Write` validation is currently unsound

> **Status**: ✅ RESOLVED (2026-05-07) — condition now only checks `produced.Contains(key)`, `writeOwners` reference removed

- File: `Assets/FYAsset/Scripts/Build/Pipeline/Editor/DAGScheduler.cs:153-166`

`ValidateInternal()` is supposed to warn when a task reads a key before any preceding task produces it. The current condition suppresses the warning whenever `writeOwners` contains the key:

```csharp
if (!selfProduce && !produced.Contains(key) && !writeOwners.ContainsKey(key))
```

`writeOwners` is populated from **all** tasks, not only preceding tasks. That means this invalid topology is silently accepted:

1. `TaskA` reads `X`
2. `TaskB` writes `X`
3. `TaskA` does not depend on `TaskB`

Because `writeOwners["X"]` exists, no warning is emitted even though `TaskA` can run before the producer. This weakens the main safety property E5-1 is supposed to provide: catching broken data-flow wiring before execution.

**Recommendation**: only use `produced` (topological prefix) for the read-before-write check, and treat `writeOwners` as a separate "someone writes this somewhere in the graph" diagnostic if needed.

### 2. Medium: duplicate `TaskName` registrations are silently overwritten

> **Status**: ✅ RESOLVED (2026-05-07) — now throws `InvalidOperationException` on duplicate

- File: `Assets/FYAsset/Scripts/Build/Pipeline/Editor/BuildTaskResolver.cs:45-49`

`BuildTaskResolver.Initialize()` indexes tasks by `TaskName`, but duplicate names are handled by last-writer-wins:

```csharp
_index[instance.TaskName] = type;
```

This means two `IBuildTask` implementations can claim the same `TaskName` and the resolver will accept the collision without any error. The resulting task selection depends on assembly/type scan order, which is not a reliable contract for the pipeline.

That directly undermines E5-1's "TaskName as unique identifier" design decision.

**Recommendation**: fail fast on duplicate `TaskName` values during `Initialize()` and surface a clear error that includes both conflicting types.

### 3. Medium: there is no direct test coverage for the scheduler and resolver invariants

> **Status**: ⚠️ RECOMMENDATION — test coverage deferred, not yet acted upon

- Evidence: no dedicated tests were found for `DAGScheduler`, `BuildTaskResolver`, `BuildContext`, or `BuildTaskResult` under the current test directories.

E5-1 defines critical invariants around cycle detection, conflict detection, `SequentialMode`, fatal-abort behavior, and pairwise validation. Those are exactly the kinds of contracts that regress quietly when later tasks are added.

At the moment the only verification I could confirm locally is compile-time success. That is weaker than the risk level of this subsystem.

**Recommendation**: add focused editor tests for:

- cycle detection
- duplicate write-key rejection
- read-before-write warning
- `SequentialMode`
- fatal abort and skipped-task accounting
- duplicate `TaskName` detection

## Summary

E5-1's overall structure is sound, but its most important validation rule is not actually enforced in the "writer exists later in the graph" case. Until that is fixed, the pipeline can accept invalid task wiring that only fails at execution time.
