# 序列化工具

这套工具的目标很简单：把一份 C# 数据对象，稳定地写成字节流，再稳定地读回来。

当前项目里它主要服务于运行时需要快速读写的结构化数据，例如 `ABManifest` 这类构建产物。它不是一个“万能存档系统”，而是一套偏工程化的二进制序列化工具。

---

## 先说怎么用

如果你只是想接入一个新的二进制数据类型，可以按下面 4 步走。

### 1. 给数据类型打标记

```csharp
[BinarySerializable(Magic = 0xABCD1234u, SchemaVersion = 1)]
public class MyData
{
    [BinaryField(0)] public string Name;
    [BinaryField(1)] public int Count;
    [BinaryField(2)] public List<string> Tags;
    [BinaryField(3)] public MyData Child;
}
```

这里最重要的是两件事：

- `BinarySerializable` 表示这个类型要进入二进制序列化体系。
- `BinaryField(Order)` 决定字段写入顺序。

一句人话提醒：`Order` 一旦和线上或磁盘数据绑定，就不要随便改，不然老数据会按错误顺序读回来。

### 2. 生成对应的序列化代码

菜单位置：

`XLua -> Serialization -> Generate Binary Serializers`

生成结果会落在：

`Assets/Tools/Scripts/Serialization/Generated/`

文件名格式是：

`{TypeName}_BinarySerializer.cs`

生成器会扫描带 `[BinarySerializable]` 的类型，为每个类型生成一份包装代码，底层仍然走统一的反射读写逻辑。你不需要手写每个类型的序列化器。

### 3. 在 BinaryCodec 里注册这个类型

```csharp
var codec = new BinaryCodec();

codec.Register<MyData>(
    magic: 0xABCD1234u,
    schemaVersion: 1,
    writeWithHeader: (writer, obj) => MyData_BinarySerializer.WriteWithHeader(writer, obj),
    readWithHeader: reader => (MyData)MyData_BinarySerializer.ReadWithHeader(reader)
);
```

这里的 `magic` 可以理解成“这份二进制数据是谁写出来的身份证”。不同类型不能共用同一个值。

### 4. 正常序列化 / 反序列化

```csharp
byte[] bytes = codec.Serialize(myObj);
MyData result = codec.Deserialize<MyData>(bytes);
```

当前行为：

- `Serialize(null)` 会返回空字节数组
- `Deserialize<T>` 如果连头都不像合法二进制数据，会返回 `default`
- 如果头是合法的，但 `Magic` 不匹配，会抛 `InvalidDataException`

## 这套工具适合什么场景

适合：

- 构建期导出、运行期读取的结构化数据
- 字段结构相对稳定、需要版本控制的数据
- 希望读写更紧凑、不依赖额外第三方库的场景

不适合：

- 频繁变结构、没人维护版本兼容的数据
- 需要跨语言、跨平台通用协议的网络消息
- 想靠它替代所有 JSON / 配置文件场景

## 原理说明

### 整体架构

```text
BinaryCodec
  ├─ BinaryHeader
  ├─ {TypeName}_BinarySerializer（生成代码）
  └─ BinaryReflectionSerializer
```

可以把它理解成四层分工：

- `BinaryCodec`：总入口，负责注册类型、根据头信息路由到正确的读写逻辑
- `BinaryHeader`：每份二进制数据前面的固定 8 字节头，用来标识类型和版本
- `*_BinarySerializer`：生成器产物，负责把某个具体类型接到统一框架里
- `BinaryReflectionSerializer`：底层通用实现，真正按字段顺序递归写入和读取

### 头部里放了什么

当前头部固定 8 字节：

- `Magic`：4 字节，标识数据类型
- `SchemaVersion`：2 字节，标识结构版本
- `Flags`：2 字节，当前预留

它的作用很直接：

- 先判断这是不是我们这套工具写出来的数据
- 再判断是不是当前代码能读的版本

### 为什么还要生成代码

因为项目不想手写每个类型的序列化器，也不想把所有逻辑都直接暴露成“纯反射黑盒”。

生成器做的事情比较轻：

- 扫描带 `[BinarySerializable]` 的类型
- 生成 `{TypeName}_BinarySerializer`
- 把 `Magic` / `SchemaVersion` / `WriteWithHeader` / `ReadWithHeader` 这些包装好

这样做的好处是：

- 接入新类型的流程统一
- 文件是否过期可以靠类型哈希检测
- 实际调用时有清晰的类型边界，不用每次都手写样板代码

### 真正的字段读写是谁干的

底层是 `BinaryReflectionSerializer`。

它会按 `[BinaryField]` 的 `Order` 排序后，递归处理字段。当前已实现支持的类型包括：

- 基础值类型：`bool`、整数、浮点数等
- `string`
- `enum`
- `T[]`
- `List<T>`
- 嵌套的 `[BinarySerializable]` 类型

如果字段类型不在支持列表里，会抛 `NotSupportedException`。

## 架构设计为什么这么做

### 1. 用 BinaryCodec 做唯一入口

这样做的好处是，外部不用关心某个类型是怎么写进去的，只要注册过，就统一从 `Serialize / Deserialize` 进出。

### 2. 用头部而不是裸字节流

裸字节流的问题是“拿到一串 bytes 不知道是谁的”。加上头部后，至少能先做类型识别和版本检查，不会把 A 类型的数据错读成 B 类型。

### 3. 用字段顺序而不是字段名

这是一种更紧凑的二进制写法，代价是字段顺序必须稳定。所以这套工具更适合工程内受控的数据结构，不适合随便改字段顺序的场景。

### 4. 用生成代码 + 通用反射的折中方案

完全手写太重，完全纯反射又不够清晰。

现在这套方案属于折中：

- 对外有明确的类型级入口
- 对内复用统一反射逻辑
- 维护成本比手写全套 serializer 低很多

## 常见注意事项

### 字段顺序不要随便改

`BinaryField(Order)` 不是装饰用的，它直接决定二进制里的写入顺序。已经落地的数据如果改了顺序，读取结果就可能错位。

### 新增字段要考虑版本

当前头里有 `SchemaVersion`。如果你给数据结构加了字段，通常要一起考虑版本兼容，而不是只改类定义。

### Magic 不能重复

`Magic` 是类型识别的关键值。重复之后，读的时候就可能路由到错误的处理器。

### 不是所有类型都能直接塞进去

目前只支持工具里已经实现的字段类型。如果你塞了复杂泛型、字典或自定义容器，大概率会直接抛“不支持的二进制字段类型”。

## null 是怎么处理的

这套工具不是简单地把 `null` 当默认值吞掉，而是显式写入“有没有值”。

当前规则：

| 情况 | 写入方式 | 读取结果 |
|---|---|---|
| 引用类型字段为 `null` | 写 `hasValue = 0` | 读回 `null` |
| `string` 为 `null` | 写 `hasValue = 0` | 读回 `null` |
| `List` / `Array` 为 `null` | 写 `count = -1` | 读回 `null` |

## 常见报错怎么理解

| 异常 | 一般代表什么 |
|---|---|
| `InvalidOperationException: 未注册二进制类型` | 你在 `Serialize` 前没有先 `Register` |
| `InvalidOperationException: 未注册的二进制 Magic` | 数据头能读出来，但当前 `BinaryCodec` 没有注册这个类型 |
| `InvalidDataException: Magic 不匹配` | 这份数据不是你以为的那个类型，或者文件内容已经损坏 |
| `InvalidDataException: SchemaVersion 不兼容` | 旧代码在读更高版本的数据结构 |
| `NotSupportedException: 不支持的二进制字段类型` | 某个字段类型超出了当前工具支持范围 |

## 一句话总结

如果把 JSON 看成“可读性优先”的方案，那这套二进制序列化工具就是“结构稳定、读写紧凑、工程内可控”优先的方案。

接入时记住三件事就够了：打标记、生成代码、注册类型。剩下的头部校验、字段递归读写和基础兼容检查，工具已经帮你兜住了。
