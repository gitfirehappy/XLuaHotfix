# Sub-Plan S2: BinaryCodec Infrastructure + Editor Code Generator

> **Risk**: Medium (core infrastructure, but no runtime behavioral change until S3 integrates)
> **Dependencies**: S1 completed (ISerializationCodec + SerializationUtility available)
> **Status**: Awaiting approval

## Objective

Build the complete binary serialization infrastructure:

1. Attribute system (`[BinarySerializable]` / `[BinaryField(n)]`) for declarative field marking
2. `BinaryHeader` full read/write (extending S1's detection-only stub)
3. `BinaryWriterExt` / `BinaryReaderExt` type-safe extension methods
4. `BinaryCodec : ISerializationCodec` registered into SerializationUtility
5. Editor code generator that scans annotated classes and produces `XxxType_Serializer.cs` files

After S2, the binary serialization pipeline is fully functional. S3 applies it to ABManifest.

## Confirmed Design Decisions

### A. Attribute System

1. Two attributes:
   - `[BinarySerializable]` — marks a class/struct as binary-serializable
   - `[BinaryField(int order)]` — marks a field with its serialization order number

2. Top-level file types declare Magic + SchemaVersion via attribute parameters:
   ```csharp
   [BinarySerializable(Magic = 0x41424D46, SchemaVersion = 1)]  // 'ABMF'
   public class ABManifest { ... }
   ```

3. Nested types (never independently stored as files) use plain attribute:
   ```csharp
   [BinarySerializable]  // no Magic, no SchemaVersion
   public class ManifestAssetEntry { ... }
   ```

4. Custom structs (e.g., `VersionNumber`) also use `[BinarySerializable]` + `[BinaryField]` — the generator handles them recursively, same as classes. No special-case handling.

### B. Supported Field Types

| Category | Types | Write/Read Strategy |
|----------|-------|-------------------|
| Primitives | bool, byte, short, ushort, int, uint, long, ulong, float, double | BinaryWriter/Reader native methods |
| String | string | Null-flag byte (0x00=null, 0x01=present) + UTF8 length-prefixed |
| Enum | any enum | Cast to underlying type (typically int), write as int |
| Array | T[] where T is primitive, string, or [BinarySerializable] | Count int (-1=null, 0+=length) + sequential elements |
| List | List\<T\> where T is primitive, string, or [BinarySerializable] | Count int (-1=null, 0+=length) + sequential elements |
| Nested | [BinarySerializable] class/struct | Null-flag byte (for class; struct always present) + inline field sequence |

### C. BinaryHeader Full Specification

```
Offset  Size  Field          Description
0       4     Magic          uint32 LE — type identifier (e.g., 0x41424D46 = 'ABMF')
4       2     SchemaVersion  uint16 LE — data structure version
6       2     Flags          uint16 LE — reserved (0x0000)
8       ...   Payload        serialized data
```

Read logic:
1. Read Magic → lookup registered type → mismatch = error
2. Read SchemaVersion → compare with current version
   - Same = normal read
   - Older = forward-compatible read (missing fields get defaults)
   - Newer = error (client too old)
3. Read Flags → currently ignored, reserved for future (compression, encryption)

### D. Null and Empty Handling

```
string null  → write byte 0x00
string ""    → write byte 0x01 + int 0
string "abc" → write byte 0x01 + int 3 + UTF8 bytes

T[] null     → write int -1
T[] empty    → write int 0
T[] items    → write int N + N elements

List<T> null → write int -1  (same as array)

class null   → write byte 0x00
class obj    → write byte 0x01 + fields
struct       → always write fields (no null flag)
```

### E. Code Generator

1. **Trigger modes**:
   - Manual: Editor menu `XLua/Serialization/Generate Binary Serializers`
   - Auto: `IPreprocessBuildWithReport` — validates generated code is up-to-date before build; if stale, either auto-regenerate or block build with error

2. **Scan scope**: All assemblies in the project; find types with `[BinarySerializable]` attribute via reflection

3. **Output location**: `Assets/AboutXLua/Scripts/Utility/Serialization/Generated/`
   - One file per annotated type: `{TypeName}_BinarySerializer.cs`
   - All generated files have `// <auto-generated>` header comment
   - Files committed to git (not .gitignore'd) — ensures CI builds work without running generator

4. **Generated code structure** (per type):
   ```csharp
   // <auto-generated>
   // Generated by BinarySerializerGenerator. Do not edit manually.
   // Source: ManifestAssetEntry (5 fields, SchemaVersion: N/A)
   // </auto-generated>
   using System.IO;

   public static class ManifestAssetEntry_BinarySerializer
   {
       public static void Write(BinaryWriter w, ManifestAssetEntry obj) { ... }
       public static ManifestAssetEntry Read(BinaryReader r) { ... }
   }
   ```

5. **Top-level type serializer** additionally handles header:
   ```csharp
   public static class ABManifest_BinarySerializer
   {
       public static void WriteWithHeader(BinaryWriter w, ABManifest obj)
       {
           BinaryHeader.WriteHeader(w, magic: 0x41424D46, schemaVersion: 1, flags: 0);
           Write(w, obj);
       }

       public static ABManifest ReadWithHeader(BinaryReader r)
       {
           var header = BinaryHeader.ReadHeader(r);
           // validate Magic, SchemaVersion
           return Read(r);
       }

       public static void Write(BinaryWriter w, ABManifest obj) { ... }
       public static ABManifest Read(BinaryReader r) { ... }
   }
   ```

6. **Staleness detection**: Generator computes a hash of (field names + field types + field orders + SchemaVersion) per type. Hash is embedded in generated file header comment. Pre-build check compares live reflection hash vs generated file hash.

### F. BinaryCodec Registration

1. `BinaryCodec : ISerializationCodec` with `CodecId = "binary"`
2. Maintains a registry: `Magic → (Type, ReadWithHeader delegate, WriteWithHeader delegate)`
3. Registration happens at startup or via explicit call:
   ```csharp
   BinaryCodec.Register<ABManifest>(
       magic: 0x41424D46,
       writer: ABManifest_BinarySerializer.WriteWithHeader,
       reader: ABManifest_BinarySerializer.ReadWithHeader
   );
   ```
4. `SerializationUtility.DetectFormat` already checks Magic via `BinaryHeader.HasValidMagic` (from S1). Once S2 registers Magic values, auto-detection activates.

### G. Schema Evolution (Forward Compatibility)

1. New fields: append with incrementing `[BinaryField(N+1)]` order number
2. Deleted fields: mark `[Obsolete]`, keep order number occupied, reader skips
3. SchemaVersion bump: increment when field set changes
4. Reader encountering older SchemaVersion: read available fields, remaining fields get `default(T)`
5. Reader encountering newer SchemaVersion: error — client needs update
6. Implementation: generated Read method checks remaining stream length before reading each field added after v1

## Not In Scope

- Annotating ABManifest / ManifestAssetEntry / ManifestBundleEntry (S3)

- Dictionary<K,V> support (not needed by current data classes; add when needed)
- Polymorphic serialization (not needed; all types are concrete)
