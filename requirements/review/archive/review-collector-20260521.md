## Summary

This review focused on correctness, build-pipeline behavior, data contracts, diagnostics, maintainability, editor usability, and test gaps. No code was changed.

The Collector subsystem has a coherent shape: `CollectorSetting -> Package -> Group -> Collector`, rule interfaces are clear, path utilities were centralized, and scan messages are already structured through `BuildMessage`. The main risks are not surface-level style issues; they are cross-stage contract mismatches between scanning, dependency analysis, and downstream bundle/manifest generation.

## Findings

### [P0] Implicit dependency entries lose their PackageName and can corrupt manifest grouping

**Files**
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:181`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:189`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:324`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:336`
- `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/AB/TaskGenerateManifest.cs:84`

**Problem**

`AnalyzePackage()` receives the current `packageName`, but implicit candidates are created with `PackageName = string.Empty` and the comment says "由调用方填充"; no later code fills it. `CreateImplicitEntry()` then writes this empty value into `CollectedAssetInfo.PackageName`, and duplicated implicit dependencies also use `candidate.PackageName` as `GroupName`.

**Impact**

Implicit dependencies generated by dependency analysis no longer carry the package boundary of the package being analyzed. Shared implicit entries still happen to use the local `packageName` for `BundleName`, but the `CollectedAssetInfo.PackageName` and duplicated dependency `GroupName` become empty. Downstream manifest generation writes `Group = a.GroupName ?? ""`, so duplicated implicit dependency entries can appear in the manifest with an empty group. This breaks the documented hierarchy semantics and makes diagnostics/package attribution unreliable.

**Recommendation**

When creating an `ImplicitCandidate`, set `PackageName = packageName`, or pass `packageName` directly into `CreateImplicitEntry()` and avoid storing a second package truth on the candidate. Add a focused test for `DependencyAnalyzer.Analyze()` proving implicit entries preserve the source package and duplicated entries do not get an empty `GroupName`.

### [P0] Global dependency traversal can miss references from later bundles

**Files**
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:102`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:109`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:121`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:194`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:280`

**Problem**

`BfsTraverseAll()` uses a package-wide `globalVisited` set and skips any root asset or dependency GUID that has already been expanded. That prevents repeated traversal, but the same traversal is also responsible for recording each implicit candidate's `ReferencingBundles`.

If bundle A reaches implicit dependency X first, X is marked globally visited. When bundle B later depends on X, traversal can skip X before recording B as a referencing bundle, depending on where the skip occurs in the graph. The global cache is being used as both "dependencies already expanded" and "all reference relationships already accounted for"; those are different facts.

**Impact**

`refCount = candidate.ReferencingBundles.Count` can be under-counted. This directly changes `SharePolicyConfig.MinReferenceCount` behavior: dependencies that should be shared may be copied, dependency edges to shared bundles may be missing, and bundle duplication can vary with traversal order.

**Recommendation**

Separate traversal expansion caching from reference accounting. Record direct ownership and implicit candidate references for every source bundle edge, even if a dependency subtree was expanded earlier. Only use the global expanded set to avoid recursively re-expanding child dependencies. Add a dependency graph test with two bundles sharing the same implicit asset.

### [P1] User-selectable `ECollectorType.Implicit` is not executable by `AssetClassifier`

**Files**
- `Assets/FYAsset/Scripts/Build/Collector/CollectorEnums.cs:27`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/AssetClassifier.cs:27`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/AssetClassifier.cs:37`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:392`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/UI/CollectorPanel.cs:346`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/UI/CollectorTargetPickerWindow.cs:78`

**Problem**

`ECollectorType` exposes `Implicit = 3`, and the editor UI uses generic enum fields, so a developer can select it. `AssetClassifier.MapRole()` only handles `Main`, `Static`, and `Depend`; selecting `Implicit` throws `ArgumentOutOfRangeException` during scanning. `CollectorSettingValidator` does not reject this configuration, so the invalid state is allowed until scan/build execution.

**Impact**

A valid-looking Collector configuration can crash the scanner instead of producing a structured `BuildMessage`. This violates the subsystem's structured diagnostics pattern and makes an internal dependency-analysis role available as a manual configuration option.

**Recommendation**

Treat `Implicit` as system-generated only. Either hide it in the editor UI and reject it in `CollectorSettingValidator`, or make `AssetClassifier` map it explicitly if manual implicit collectors are truly intended. Given current docs say implicit dependencies are auto-discovered, validation rejection is the safer direction.

### [P1] Rule execution exceptions are not contained by the scanner

**Files**
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:386`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:392`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:406`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:418`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:431`

**Problem**

`ResolveRuleSafe()` catches rule resolution failures, but actual rule execution is unguarded. Exceptions from `IFilterRule.IsCollectable`, `IGroupRule.GetTargetGroup`, `IAddressRule.GetAddress`, `IPackRule.GetPackKey`, or `AssetClassifier.Classify` bubble out of `CollectionScanner.Scan()`.

**Impact**

One malformed custom rule can abort the entire build/editor scan with a raw exception instead of a `BuildMessage` carrying rule type, asset path, collector path, and source. This is especially risky because the rule system is reflection-driven and intended to be extensible.

**Recommendation**

Wrap per-asset rule execution with structured error conversion. Use dedicated error codes rather than collapsing everything into `RULE_NOT_FOUND`, and include rule class name, collector path, and asset path in the message source. If a rule failure should abort the package, return an Error message and stop cleanly.

### [P1] Invalid package entries are silently skipped during build scanning

**Files**
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:37`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:40`
- `Assets/FYAsset/Scripts/Build/Pipeline/Editor/Tasks/TaskCollectAssets.cs:31`

**Problem**

`CollectionScanner.Scan()` skips `null` packages and empty `PackageName` with `continue` and no diagnostic. `CollectorSettingValidator` can report `EMPTY_PACKAGE_NAME`, but the build task does not run the validator; it relies on scan messages.

**Impact**

Build execution can silently ignore part of the Collector configuration. If a package is accidentally unnamed, assets disappear from the build result with no build failure and no warning.

**Recommendation**

Make scanner validation authoritative for execution, or call `CollectorSettingValidator.Validate()` before scanning in `TaskCollectAssets`. Empty package names should be Error messages, not silent skips.

### [P1] Rule/config validation uses misleading error codes

**Files**
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:337`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:437`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:519`
- `Assets/FYAsset/Scripts/Build/Editor/Shared/BuildMessage.cs:16`

**Problem**

Several non-rule failures reuse `BuildErrorCodes.RuleNotFound`: invalid bundle name segment, invalid pack key, invalid label, and empty rule class names. Dependency analysis also uses raw string codes (`CYCLE_DEPENDENCY`, `SHAREPOLICY_CONFLICT`) that are not centralized in `BuildErrorCodes`.

**Impact**

Aggregate reporting cannot distinguish a missing rule class from invalid naming or label input. It also repeats the historical error-code pitfall: raw string codes make later filtering and documentation inconsistent.

**Recommendation**

Add centralized codes such as `INVALID_BUNDLE_NAME_SEGMENT`, `INVALID_LABEL`, `EMPTY_RULE_NAME`, `RULE_EXECUTION_FAILED`, `CYCLE_DEPENDENCY`, and `SHAREPOLICY_CONFLICT`. Keep `RULE_NOT_FOUND` only for failed rule type resolution.

### [P2] `MinAssetSizeBytes` silently falls back to "share allowed" when file size cannot be read

**Files**
- `Assets/FYAsset/Scripts/Build/Collector/SharePolicyConfig.cs:18`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:267`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:271`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/DependencyAnalysis/DependencyAnalyzer.cs:399`

**Problem**

`SharePolicyConfig.MinAssetSizeBytes` is an exposed configuration field. `GetAssetFileSize()` returns `-1` on missing files, invalid paths, or exceptions, and `ApplySharePolicy()` only disables sharing when `fileSize > 0 && fileSize < threshold`. Unknown file size therefore behaves as if the threshold passed.

**Impact**

A file-size read failure silently changes policy behavior and can share assets that should have been excluded by size. Since this is build-time policy, silent fallback makes package layout hard to diagnose.

**Recommendation**

If a configured size threshold cannot be evaluated for an asset, emit a warning or error with asset path and package name. Prefer fail-fast if the asset path should be a real project asset at that point.

### [P2] Validator and scanner duplicate semantics and can drift

**Files**
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectorSettingValidator.cs:97`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectorSettingValidator.cs:201`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectorSettingValidator.cs:245`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:191`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:332`
- `Assets/FYAsset/Scripts/Build/Collector/Editor/CollectionScanner.cs:490`

**Problem**

Validation and execution each implement their own path existence checks, rule resolution helpers, and overlap checks. This exact pattern is already recorded in `context/mistakes/implementation-pitfalls.md` as a historical prevention rule.

**Impact**

The system can show a clean editor validation state while build scanning behaves differently, or vice versa. The `Implicit` enum issue is one example: validation does not reject it, scanner execution can throw.

**Recommendation**

Extract shared validation/execution helpers for collector path validation, rule validation, and executable collector validation. The build task should consume the same validation path that the editor UI uses, with scanner-only checks limited to asset traversal results.

### [P2] No automated tests cover the Collector contracts

**Evidence**

Search found only `CollectorTestSeeder`, a menu-based sample data tool. No edit-mode tests were found for `CollectionScanner`, `DependencyAnalyzer`, `CollectorSettingValidator`, `GlobMatcher`, or `BundleNameBuilder`.

**Impact**

Collector behavior is contract-heavy and cross-stage: path containment, ownership exclusion, group routing, pack naming, implicit dependency extraction, and share policy all need deterministic semantics. Without tests, regressions are likely to land unnoticed, especially because many failure modes only appear after several pipeline stages.

**Recommendation**

Add edit-mode tests around the highest-risk contracts first:

- invalid manual `ECollectorType.Implicit` is rejected before scan execution
- implicit dependencies preserve source `PackageName`
- two bundles sharing one implicit dependency both appear in `ReferencingBundles`
- empty `PackageName` blocks build scanning
- invalid label/pack-key errors use distinct codes
- `GlobMatcher` anchoring and ignore directory behavior

## Non-Blocking Observations

- `DependencyAnalyzer` calls `AssetDatabase.GetMainAssetTypeAtPath(dep)` into `depType` at line 175, but `depType` is unused. This is a small editor-time performance cleanup.
- `CollectorReverseIndex` intentionally logs and skips assets when filter rule resolution fails. That is acceptable for inspector convenience, but it should stay clearly separate from build-time scanner behavior, where failures should be structured and blocking.
- `TaskBuildBundles` and `TaskGenerateManifest` still use raw file APIs. This review did not expand into AB task refactoring, but it intersects with historical raw I/O rules and should be reviewed separately if those files are in scope later.

## Suggested Fix Order

1. Fix implicit dependency package/reference accounting first; it affects actual bundle and manifest output.
2. Block manual `Implicit` collector configuration and add structured scanner exception handling.
3. Make build scanning use the same validation semantics as the editor.
4. Clean up diagnostic codes and add focused edit-mode tests.
